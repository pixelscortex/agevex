Hooks belong to an `Agent` and run inside the existing action, adding no
Workflow steps. The five hooks are `beforeTurn`, `afterTurn`, `beforeTool`,
`afterTool` and `beforeDelegate`. Hooks receive a `HookContext` that omits
`toolCallId`. `afterTurn` is a notification returning void. Other hooks may
return `note`, `block`, `input`, `output` or `model` as appropriate.

```ts title="convex/hooks.ts"
import type { AgentHooks } from "agevex";

export const hooks = {
  beforeTurn: (_hc, { prompt }) => (prompt.trim() ? undefined : { block: "A prompt is required." }),
  beforeTool: (_hc, { tool }) =>
    tool === "delete_account" ? { block: "Use the account settings page." } : undefined,
} satisfies AgentHooks;
```

`beforeTool` may replace the input with `input`, and `afterTool` may replace
the output with `output`; a streaming output is reshaped value by value. A
`block` denies the tool with `{ status: "denied", code: "HOOK_BLOCKED" }`. A
throwing hook fails the turn with `HOOK_FAILED`, and its details stay outside
the transcript.

## Saved reply identities

`afterTurn(hc, { turn, text, messageIds })` receives every successful assistant
message id saved by the reporting turn, in save order across tool continuations
and approval pauses/resumes. Assistant tool-call messages qualify even without
text; tool-role results, pending/failed placeholders and fenced-out saves are
excluded. Ids are recorded atomically with native saves, without transcript reads.

`text` keeps its existing scope: successful assistant text from the completing
slice, joined with newlines. Earlier narration is available by exact message id.
Tool continuations and approval pauses emit no `afterTurn` until completion.
New user, queued or child work starts a fresh list; approval resumes keep it.
The notification cannot request more work. Call the public send/runtime API
from your own code when a follow-up is needed.

Each slice saves at most one assistant row. Run `stepsPerTurn` and any non-default
host `slicesPerTurn` cap bound the list, including approval resumes: at most
64 ids, each at most 37 ASCII characters. Reporting state reserves 3 KiB within the
assignment envelope.

## Model choice per generation

`beforeTurn` runs before each model generation, including tool steps and approval
resumes. It may return an id in the registered model allowlist. That choice is
local to this generation: no assignment field, sibling lock or run model is
changed. Return the model on every invocation to keep using it. Siblings run
and choose independently. The prompt identifies the original reporting request.

## Notes and origins

`runtime.note(ctx, { threadId, text, from })` authorizes the `note` operation
and accepts at most 4,000 UTF-16 units of raw text, then escapes it and wraps it
in a user-role `<note from="…">` message. The `notesPending` cap is the single admission limit, 8
by default and 24 at the hard maximum, independent of `queueLength`. At
capacity, `runtime.note` throws a typed `NOTES_PENDING_LIMIT` error.

Notes wait for the next safe turn claim: a claim with no decided approval
awaiting a committed tool result. That claim saves every pending note in
arrival order, after prior tool results. Ordinary tool-step slices never drain
notes, and a note never starts a turn or schedules work.

The authorized `messages` reader adds `origin: user | result | note`
with `from` for notes and `runId` for results; unclassified messages use `user`.

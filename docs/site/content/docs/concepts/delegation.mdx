One `Agent` type represents roots and children. An agent becomes a child by
appearing in another agent’s `subagents` list.

```ts title="Planned agent hierarchy"
const reviewer = new Agent(components.agent, { name: "Reviewer", languageModel, instructions })
const builder = new Agent(components.agent, {
  name: "Builder", languageModel, instructions,
  subagents: [reviewer],                     // depth 2 allowed
})
const main = new Agent(components.agent, {
  name: "Main", languageModel, instructions,
  subagents: [builder, reviewer],
})
```

## Model-facing tools (planned)

| Tool | Contract |
| --- | --- |
| `delegate` | `{ agent, task, context?: "isolated" \| "forked", group?, wait?: "all" \| "each" }` → `{ runId }` or a typed denial |
| `message_child` | Send a follow-up to a running child. |
| `ask_parent` | Ask the parent one question, bounded per turn. |

The planned defaults are depth 2, five active children per root, 12 launches
and 24 hops per run, and tasks of at most 4,000 characters. A **run** covers one
user prompt and everything it causes, including result-triggered turns.
When its budget ends, `delegate` returns
`{ status: "denied", code: "RUN_BUDGET" }`; the model answers with what it has.

## Groups and context

`delegate({ group: "draft", wait: "all" })` waits for the group to settle and
wakes the parent once with all results. The parent receives a host-verified
child reply, rather than trusting a child’s claim about its own result.

`isolated` is the default and gives the child only its task. `forked` adds a
bounded snapshot of the parent: recent messages, at most 48 KiB, with tool
outputs stripped. `summarized` context is deferred.

## One reader

`messages({ threadId })` reads the root and every child thread the caller
owns, in the same envelope. `delegations` returns each run's `childThreadId`
(`null` until the child starts). There is no separate transcript endpoint and
no opt-in flag. `open`, `send`, `activity` and `delegations` accept root
threads only.

## Available today

The current runtime supports depth 1, three launches per accepted user prompt
and five active children per root. Children are queued asynchronously, and
results arrive in later parent turns. Groups, joins, deeper delegation,
`message_child` and `ask_parent` are planned.

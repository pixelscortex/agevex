Titles run once after the first user message commits, without waiting for an
assistant answer. Their default model is the root Agent model, including its
accepted model override. `title: { model, prompt }` configures that call;
`title: false` disables it. Outputs fit 120 Unicode code points and 512 UTF-8 bytes.

The [getting-started registration](/docs/getting-started) exports `textTask` from
`runtime.internalFunctions()` and supplies `refs.textTask`. That reference is
required when either titles or summaries are enabled. Both disabled permits a
registration with only the foreground references. Generated-reference inference
cycles can use `RegisteredAction<"internal", TextTaskArgs, null>` from
`convex/server`, with `TextTaskArgs` imported from `agevex`.

## User titles

`title({ threadId })` returns `{ text: string | null, source: "auto" | "user" |
null, version: number }`. Call `rename({ threadId, text, expectedVersion })` with
that version. A user rename always wins over a late generated title. An identical
retry replays; competing text at an outdated version throws `VERSION_CONFLICT`.
The shared `{ messageId, replayed }` response receipt identifies the native thread
in `messageId`; renaming creates no transcript message. All four metadata
endpoints authorize the persisted root owner through the host policy.

## Opt in to summaries

Leave `summary` absent or false to make no summary calls. `summary: {}` enables
on-demand `summarize({ threadId, requestKey })`, returning `queued` or `replayed`.
`summary: { everyTurns: 10 }` also requests work after each tenth completed root
turn. Cadence accepts integers from 1 through 1,000,000; tools and child turns do
not increment it. `model` and `prompt` configure summary generation separately.

`summary({ threadId })` returns `{ text, throughMessageId }` or null. The exact
boundary covers successful completed-root work, excluding active/queued prompts
beyond it. Input uses the prior summary plus at most 24 exact recent native
messages, 48 KiB serialized; full native document reads fit 2 MiB. Summary output
fits 8 KiB. A delayed worker reads the newest available completed boundary when
claimed. One summary runs per thread; later requests coalesce into one follow-up
for newer completed work. An early on-demand request waits for the first completed
root boundary without occupying a worker or polling.

## Opt in to context compaction separately

`summary: { everyTurns: 10, compact: true }` uses a summary at a safe subsequent
root turn. Only a contiguous, completely covered plain-text prefix qualifies.
The selected context includes the summary, a bounded recent suffix, the current
user task and existing same-order responses. Original native messages remain
available for display. File references, tool/approval exchanges, ring gaps,
byte-truncated windows, changed/deleted documents and cancelled epochs fall back
to native selection. This conservative implementation keeps such exchanges
native rather than compacting partial coverage. Display summaries still work.

## Capacity, usage and failure

Workers use the child/background lane and never await a model on the foreground
turn. Each call rechecks `authorizeExecution` with persisted ownership and
`purpose: "title" | "summary"`, then the optional budget. No interactive identity
is assumed. Titles use 128 output tokens; summaries use 2,048. Calls stop waiting
after 30 seconds, including providers that ignore abort. Prompts have a 4,096
character configuration bound. Tasks use no tools, no repairs and no paid retries.

Usage passes through the ordinary usage slot with `title`/`summary` purpose,
the triggering root run and an exact provider response id when available.
Reconciliation can settle after that run closes. Recording failures mark usage
partial without changing metadata or buying another call. Cancellation blocks
queued work and late metadata commits; incurred usage remains recorded.

Failures preserve previous text and conversation progress. A fresh explicit
summary request can try again after a known-invalid result. Repeating its old
request key only replays scheduling. Unknown outcomes block further summary
work, including fresh keys, so neither cadence nor a later send silently retries
paid work. Title generation is attempted once per thread.

`open` and `send` return a receipt immediately. They never wait for a model
turn.

| Status      | Fields                                                    |
| ----------- | --------------------------------------------------------- |
| `accepted`  | `threadId, assignmentId, receiptId, position`             |
| `duplicate` | The same identity fields and required original `position` |
| `rejected`  | A typed `code`                                            |

Import the validator-derived `Receipt` type from `agevex`.

`position` is the zero-based inbox place at acceptance, including a reserved
head until a claim consumes it. A duplicate keeps the position of the original
acceptance.

## Rejection codes

`KEY_CONFLICT`, `QUEUE_FULL`, `CANCELLED`, `INVALID_MESSAGE`,
`INVALID_REQUEST_KEY`, `UNKNOWN_AGENT`, `INVALID_MODELS`, `ATTACHMENT_LIMIT`,
`RECOVERY_REQUIRED`.

Invalid input is refused before the prompt is stored. A full queue and a
recovery-required thread are refused by `send` before the prompt is stored.
Authorization failures throw instead of returning a receipt. Up to 20
additional prompts queue while the thread is busy, and an arrival never
silently enters an ongoing turn.

## Idempotent retries

`requestKey` is scoped to the subject. An identical key with identical input
replays the stored receipt. The same key with changed input returns
`KEY_CONFLICT` before any native write. The fingerprint covers the operation,
the agent or thread, the text, the model map and the file ids.

`open` and `send` first call `authorize(ctx, scope)` on every attempt,
including retries. Its scope includes `requestKey` without replay metadata.
The returned `{ subject }` is the host's own subject mapping; it need not equal
the auth identity's subject. The receipt lookup then uses that subject alone.

Optional registration hook `admit(ctx, { subject, operation, agent, threadId?, requestKey })`
runs only for fresh requests, after duplicate/conflict resolution and all
agevex checks that can return a rejection receipt (input, queue and attachment
limits). Use it to refuse new paid work (e.g. exhausted balance) without
breaking idempotent retries:

```ts
admit: async (ctx, { subject }) => {
  if (!(await hasBalance(ctx, subject))) throw new Error("OUT_OF_BALANCE");
},
```

The hook receives the full host MutationCtx: **admit may write host state in the
same transaction; those writes commit only if the request is accepted.** Native
saves, inbox rows and receipts are written afterwards. If the hook throws, or
any later step fails, the entire mutation rolls back, including host patches
and scheduled work. After the hook, non-accepting results throw rather than
returning a receipt. No reservation or settlement counterpart is required.

A host that denies a retry in `authorize` still causes the call to throw.
Purged receipts no longer identify a duplicate, so the request must pass fresh
admission again. Another subject's retained receipt never bypasses admission.

## Approvals

A pending native tool approval blocks generation and leaves the inbox row
waiting. Decisions must go through
`respond({ threadId, approvalId, decision })`, which returns
`{ messageId, replayed }` (`replayed` is true when an identical retry was served
from the receipt). A response saved directly through the Agent component is not
seen by the runtime. An unknown approval throws `APPROVAL_NOT_FOUND`;
while its receipt is retained, an identical repeated decision replays
`messageId`, and a changed decision throws `KEY_CONFLICT`.

Human decisions use `respond({ threadId, approvalId, decision })`:
`{ kind: "approve" }`, `{ kind: "reject", reason? }`, or
`{ kind: "approve", edit: { input } }`. Declared local tools with an executable
binding can be edited; provider-executed and deferred tools cannot. The host
validates edited input with the registered tool schema in the response transaction.
Invalid edits leave the request pending. `defineOnceTool({ approval: { editable: true }, ... })`
also enables approval without separately setting `needsApproval`.

An edited approval preserves the original native proposal. A receipt binds the
exact tool call to effective input and original/effective hashes. The native approval
response carries this audit annotation in its reason, and the native result is
`{ result, approval: { toolCallId, input, originalHash, effectiveHash, edited } }`.
Hooks and the once-tool fingerprint see the effective input; `beforeTool` may deny
work, but rewriting approved input returns `APPROVED_INPUT_CHANGED`. Cancellation
and current host execution authorization still apply. No paid effect is retried.

`pendingApprovals({ threadId, rootRunId? })` authorizes the root and includes its
current owned child decisions. Each item contains `id`, `toolCallId`, `threadId`,
`agent`, `kind` (`approval` or `ask`), `tool`, `input`, `editable`,
`providerExecuted`, and optional `question`/`schema`. The optional run selector
must match the root's current request. Subscribe to this query to render controls.

Bounds are shared: 16 calls per paused assignment, 16 paused assignments, 16 KiB
per input/answer/complete pending source document, 16 KiB per projected item and
4 MiB per pending query output. Native storage may repeat raw input, so the whole
source envelope must fit. Oversized saves roll back without an actionable pause.
Exact source IDs avoid transcript scans; oversized direct native sources return
`PENDING_SOURCE_TOO_LARGE`. Decisions and answers retain the seven-day response
receipt: identical retries return the first `{ messageId, replayed: true }`, and
changed payloads return `KEY_CONFLICT`.

## Deferred tools

A tool declared without `execute` uses Agent's native deferred results. The
owner answers with `answer({ threadId, toolCallId, value })`, which returns
`{ messageId, replayed }` and resumes the turn once every pending call has an answer. The
value must be a nonblank string without a form schema, or JSON matching the
recorded app-supplied schema. Answers are bounded to 16 KiB. Without a retained response
receipt, unrecorded, foreign, cancelled and already answered calls throw
`TOOL_CALL_NOT_FOUND`; retained receipts replay identical answers and reject
changed answers with `KEY_CONFLICT`.
Approvals and deferred calls share one 16-call pause bound.

Both endpoints are idempotent per call: repeating a call replays the stored
`messageId`, and reusing a call id with a different payload returns
`KEY_CONFLICT`. `respond` and `answer` authorize against the owning subject,
for root threads and owned child threads alike.

## Cancellation

`cancel` settles only the open recorded calls, with native execution-denied
results. A fresh send reopens a cancelled thread and preserves the native
thread. A failed cancellation cleanup blocks reopening with a `CANCELLED`
receipt until a later cancel settles the recorded work.

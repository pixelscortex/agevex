## Ask for consent

`continue_budget({ reason })` pauses on a native approval. `CONTINUE_BUDGET_LIMITS`
allow one trimmed, nonblank reason of at most 2000 characters; unknown fields,
including ownership or a proposed budget, are rejected. The owner answers with
core `respond({ threadId, approvalId, approved })`. Only approval executes the
tool; denial never returns an approved execution. **Consent does not raise any
limit**: the tool changes no meter, budget or core counter.

## Record consent in your approve action

Core keeps approval decisions in the native Agent transcript and has no
read-only "was it approved" query. Consent is therefore **host state**: your
approve action is one mutation that calls core `respond({ approved: true })` and
records the consent row in the same transaction. The row is
`{ subject, threadId, approvalId, runId }` in `agevexBudgetConsents`, where
`runId` is the thread's `activity.runId` at approval time.

```ts
export const approveContinue = mutationGeneric({
  args: { threadId: v.string(), approvalId: v.string() },
  handler: async (ctx, { threadId, approvalId }) => {
    const subject = await myAuthorize(ctx); // your host policy
    const response = await ctx.runMutation(api.agents.respond, {
      threadId,
      approvalId,
      approved: true,
    });
    const { runId } = await ctx.runQuery(api.agents.activity, { threadId });
    await ctx.runMutation(internal.agevexTools.continueBudgetState.record, {
      subject,
      threadId,
      approvalId,
      runId,
    });
    return response;
  },
});
```

Denials are answered through plain `respond({ approved: false })` and record
nothing. `record` is idempotent (the first row wins); `consume` is how the resume spends it. Approval ids over 512 UTF-8 bytes cannot be indexed and are
rejected, which rolls back the `respond` too. Rows outlive threads: call the
shipped internal `cleanup({ subject, threadId? })` from your retention job (at
most 128 rows per call; call again while `done` is false).

## Continue a stopped run

When your `budget` slot denies a slice, core ends the turn with
`BUDGET_EXCEEDED` in `activity` and leaves the run in `recovery_required`. Core
never resumes it, because the step that tripped the budget may be an uncertain
paid step. `resumeAfterBudgetStop` runs the supported sequence, and you call it
inside **one host mutation**:

```ts
import { resumeAfterBudgetStop } from "./agevexTools/continueBudget.js";

export const resumeAfterBudget = mutationGeneric({
  args: { threadId: v.string(), approvalId: v.string() },
  handler: async (ctx, { threadId, approvalId }) => {
    const subject = await myAuthorize(ctx);
    return resumeAfterBudgetStop({
      threadId,
      approvalId,
      consumeConsent: (args) =>
        ctx.runMutation(internal.agevexTools.continueBudgetState.consume, { subject, ...args }),
      activity: () => ctx.runQuery(api.agents.activity, { threadId }), // includes runId
      raiseBudget: () => ctx.runMutation(internal.budgets.raise, { subject }), // idempotent
      cancel: () => ctx.runMutation(api.agents.cancel, { threadId }),
      send: (args) => ctx.runMutation(api.agents.send, { threadId, ...args }),
    });
  },
});
// "no-consent" | "not-stopped" | { status: "resumed", receipt }
```

Order: check the stop, check consent, raise your budget policy, cancel the
stopped run (clears its recovery state and discards its pending notes), then
send a fresh request as a new run.

- **Atomic.** Nested `ctx.runQuery`/`ctx.runMutation` calls share the mutation's
  transaction, so the stop check, budget write, cancel and send commit together.
  Two overlapping resumes cannot both pass: the loser sees `not-stopped`. Run as
  separate transactions, the loser would cancel the fresh run the winner just sent.
  A rejected `send` throws, which rolls back the budget write and the cancel.
- **One key per stop.** `activity.runId` is the id your budget slot received. The
  request key `after-budget:<threadId>:<stoppedRunId>` is unique per stop, so the
  same thread can be stopped and resumed repeatedly. A `duplicate` or `rejected`
  receipt is never a success: the helper throws, which rolls back the consent
  spend, the budget write and the cancel, so the run stays resumable.
- **Consent is single-use and run-bound.** `consume` deletes the row inside the
  resume transaction and succeeds only for the same owner, thread, approval id
  and stopped run id it was recorded for. One approval therefore cannot authorize
  a later stop, and an approval given in one run cannot unlock another run's
  stop. A failed resume restores the row.
- **Consent is never inferred.** The helper never calls `respond`, so a pending
  approval cannot be approved on the user's behalf. An approval answered through
  core alone, a denied one, or an unknown id returns `no-consent` and changes
  nothing.
- **What the model sees.** Cancel settles the model's original `continue_budget`
  call as an `execution-denied` tool result, because core never executes a call
  whose slice was stopped. That denial is not a refusal, so the fresh request
  starts with "The user approved continuing beyond the budget." (`CONSENT_TEXT`).
  The stopped run's budget note is discarded by the cancel.

Budget policy and storage stay host-owned.

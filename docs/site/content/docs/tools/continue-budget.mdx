```sh
bunx shadcn add http://localhost:3000/r/continue-budget.json
```

Start the docs site or replace its origin. The item copies
`convex/agevexTools/continueBudget.ts` and installs `ai`, `convex`, `zod`.
The host must already have `agevex`.

Use a TypeScript host with `"tsx": true` in `components.json` before installing
so shadcn preserves the tool's types.

```ts title="In your agevex Agent registration"
import { createContinueBudgetTool } from "./agevexTools/continueBudget.js";

const tools = { continue_budget: createContinueBudgetTool() };
// Include ...tools in your Agent's tools; keep host authorization policies.
```

## Ask for consent

`continue_budget({ reason })` pauses on a native approval. `CONTINUE_BUDGET_LIMITS`
allow one trimmed, nonblank reason of at most 2000 characters; unknown fields,
including ownership or a proposed budget, are rejected. The owner answers with
core `respond({ threadId, approvalId, approved })`. Only approval executes the
tool; denial never returns an approved execution. **Consent does not raise any
limit**: the tool changes no meter, budget or core counter.

## Continue a stopped run

When your `budget` slot denies a slice, core ends the turn with
`BUDGET_EXCEEDED` in `activity` and leaves the run in `recovery_required`. Core
never resumes it, because the step that tripped the budget may be an uncertain
paid step. `resumeAfterBudgetStop` runs the supported sequence from a host
action:

```ts
import { resumeAfterBudgetStop } from "./agevexTools/continueBudget.js";

const result = await resumeAfterBudgetStop({
  consent: approved, // the user's explicit spending consent
  activity: () => ctx.runQuery(api.agents.activity, { threadId }),
  raiseBudget: () => ctx.runMutation(internal.budgets.raise, { subject }), // idempotent
  cancel: () => ctx.runMutation(api.agents.cancel, { threadId }),
  send: () =>
    ctx.runMutation(api.agents.send, { threadId, text, requestKey: "after-budget" }),
});
// "no-consent" | "not-stopped" | { status: "resumed", receipt }
```

Order: consent, raise your budget policy, cancel the stopped run (clears its
recovery state and discards its pending notes), then send a fresh request as a
new run. Without consent, or if the thread is not stopped for budget, nothing is
changed or cancelled. A rejected `send` throws its receipt code. If `raiseBudget`
or `cancel` fails, call again; once `cancel` succeeded, retry core `send` with the
same `requestKey` (a repeat returns `duplicate`).

No item tables or schema changes. Budget policy and storage stay host-owned.
